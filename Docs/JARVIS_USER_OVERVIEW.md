# JARVIS — обзор системы

> **LAVR Phase 1.** This file is the **JARVIS origin** product overview. The running product is **LAVR**: a dedicated single-client instance at `https://lavr.youngfashionshow.com`, workspace `/lavr`. It is not SaaS and does not register third-party users. See [LAVR_MIGRATION.md](LAVR_MIGRATION.md) and [CURRENT_STATE.md](CURRENT_STATE.md). Deeper rewrite of this overview is deferred.

Этот документ объясняет продукт JARVIS человеку, который видит проект впервые.

Это не маркетинговый буклет и не техническая документация разработчика. Цель — понять, **что это**, **зачем**, **как пользоваться каждый день**, и **где границы**.

Статус функций ниже отражает фактическое состояние на **7 сентября 2026**. Если код и старые описания расходятся, верны код и [CURRENT_STATE.md](CURRENT_STATE.md).

Core Daily Workflow (чистый повтор **Validation Core 2**): **MANUAL PASS 10/10**. Это проверенная ежедневная цепочка, не закрытие всех edge cases подсистем.

> **Как читать статусы.**  
> **MANUAL PASS** — Owner проверил в живой системе.  
> **IMPLEMENTED / NOT VALIDATED** — код есть, живая проверка Owner’ом ещё не делалась. Не считать «проверено в бою».  
> **DEFERRED** — сознательно отложено.  
> **CANCELLED** — строить не будут.

## 1. Что такое JARVIS

JARVIS — персональный AI-ассистент с постоянной памятью, историей разговоров, задачами, напоминаниями, структурированными знаниями, интеграциями и автоматизациями.

Это **не** одноразовый чат вроде вкладки ChatGPT, которая забывает вас после закрытия страницы.

У Jarvis есть пользователь. У пользователя есть постоянные разговоры. Между сессиями сохраняется рабочий контекст: что вы просили запомнить, какие задачи открыты, кого вы ждёте, какие условия поставили.

Рядом с чатом живут:

- **Memory** — долговременные факты и предпочтения
- **Knowledge** — люди, проекты, связи, таймлайн событий
- **Tasks** — что нужно сделать
- **Reminders** — когда напомнить
- **Projects** — рабочие контейнеры (Owner)
- **Watchers** — «когда случится X, скажи мне»
- **интеграции** — Gmail, Calendar, GitHub, веб-поиск (часть — только Owner)
- **голос** — в Web Workspace
- **Telegram** — тот же ассистент в мессенджере, не второй мозг
- **Web Workspace** — основной интерфейс

ChatGPT — модель в окне чата. Jarvis — система вокруг модели: пользователь, история, инструменты, подтверждения, изоляция данных.

## 2. Основной интерфейс

Главный продукт — **Web Personal Workspace**.

| Кто | Адрес | Зачем |
| --- | --- | --- |
| Owner | `/jarvis` | Полный рабочий стол, включая проекты и внешние интеграции |
| Обычный пользователь | `/chat` | Тот же чат и личная продуктивность, без Owner-доменов |

Публичная установка: [https://jarvis.owlsolutions.net](https://jarvis.owlsolutions.net). Открытой регистрации нет: пользователя создаёт Owner в Admin.

На рабочем столе:

```
┌─────────────┬──────────────────────────────────┬─────────────┐
│ Чаты        │  Текущий разговор                │  Панели     │
│             │                                  │             │
│ Основной    │  сообщения                       │  Обзор      │
│ YFS         │  голос (Рация / Диалог Beta)     │  Задачи     │
│ …           │  вложения                        │  Автоматиз. │
│             │                                  │  Напоминания│
│ Настройки   │                                  │  Уведомления│
└─────────────┴──────────────────────────────────┴─────────────┘
```

Что видно в типичном сеансе:

- **список разговоров** слева (можно завести несколько тем)
- **текущий чат** в центре
- **голос** — переключение Text / Voice
- **Обзор** — компактная картина дня: внимание, ожидания, недавние изменения (**MANUAL PASS** для проверенного core flow после Validation Core 2 / Scenario 8; не все edge cases)
- **Задачи**, **Напоминания**, **Автоматизации** (watchers), **Отчеты**, **Уведомления**
- **Настройки**: профиль, ассистент, Memory, Knowledge, продуктивность, голос, интеграции

Memory, Knowledge и интеграции **не** висят отдельными гигантскими экранами на главной. Они живут в Настройках (плюс карточки сущностей в Knowledge).

Удаление чата: меню у разговора → подтверждение. Удаляется этот чат и его сообщения. Задачи, напоминания, память, Knowledge и постоянные файлы **не** стираются. Owner подтвердил это в Core Daily Workflow Scenario 10: **MANUAL PASS** для проверенной семантики.

### Owner и обычный пользователь

Оба получают: чат, память, знания, задачи, напоминания, watchers (внутренние источники), уведомления, голос, веб-поиск, файлы в чате, Telegram DM.

Только Owner:

- Projects
- Gmail / Google Calendar / GitHub
- Admin, группы Telegram, страница Storage `/jarvis/storage`
- внешние watchers на почту/календарь/GitHub

Owner в чужом Personal Workspace **не** обходит владение: чужой чат по чужому id — 404.

## 3. Как работает чат

Разговоры постоянные. Можно держать несколько чатов («Основной», «YFS», «Знакомство»). Jarvis понимает продолжение темы в текущем чате, помнит недавние ссылки на задачи / людей / проекты и умеет искать старое через summaries и поиск истории. Неоднозначные опасные действия он не угадывает. Проверенное поведение continuation / reference / clarification: **MANUAL PASS** в Core Daily Workflow. Это не полное покрытие всей Conversation Intelligence.

Путь одного сообщения:

```
Пользователь (Web / Telegram / голос)
        │
        ▼
  Сохранение сообщения
        │
        ▼
  Сборка контекста
  (этот чат, working context,
   Memory, Knowledge, summaries)
        │
        ▼
  Модель Conversation AI
        │
        ├── при необходимости вызывает Tools
        │     (задачи, почта, поиск…)
        │
        ▼
  Ответ пользователю
        │
        ▼
  Сохранение ответа
        │
        ▼
  Позже, в фоне:
  Memory / Knowledge / summaries
```

Важно:

- входящее сохраняется **до** вызова модели — сбой AI не должен потерять вашу реплику
- фон (извлечение памяти и знаний) не должен задерживать ответ
- Web: можно написать следующее сообщение, пока предыдущее ещё думает; устаревший ответ не перезапишет новый
- голос — это тот же чат, не отдельный ассистент

## 4. Memory

Memory — то, **что Jarvis помнит** о вас надолго.

**Вы:** «Я предпочитаю короткие отчёты.»  
Jarvis может сохранить это как устойчивое предпочтение.

Типичное содержимое:

- предпочтения («пиши кратко», «не звони утром»)
- факты о пользователе и работе
- явные инструкции
- устойчивая информация, которую имеет смысл помнить через недели

Memory **не** является полным логом чатов. Полный текст сообщений хранится отдельно как история разговора. Summaries — сжатие длинных кусков, служебный слой, не замена оригинала.

Удаление чата **не** уничтожает подтверждённые факты памяти: отвязывается только ссылка «это было сказано в том чате».

Memory личного пользователя A никогда не попадает пользователю B.

## 5. Knowledge

Knowledge — не «ещё одна память». Это индекс: **какие сущности существуют, как связаны, что произошло, откуда это известно**.

| Слой | Вопрос |
| --- | --- |
| Memory | Что Jarvis помнит |
| Knowledge | Кто/что это, как связано, что случилось |
| Project | Каноническое имя и статус проекта |
| История чата | Что именно было сказано |

Пример:

```
Marco  ──работает над──►  YFS
YFS    ──использует──►    GitHub-репозиторий
YFS    ──имеет──►         Task / событие / файл
```

Knowledge хранит:

- людей, проекты, организации, системы, файлы, темы
- связи (работает над, ждёт, обещал…)
- таймлайн событий
- источники (provenance): откуда факт

Это **не** CRM-книга контактов и не полный граф всей жизни. Нет массового сканирования почты «на всякий случай». Люди не выдумываются. Чувствительные поля вроде религии или здоровья не ведутся.

Статус слоя: **MANUAL PASS** для проверенного core flow (явный факт → извлечение → retrieval между чатами → provenance). Не все edge cases Knowledge.

Над Knowledge есть ещё **синтез** (Phase E.3, **MANUAL PASS** для проверенного core synthesis / Overview / waiting / state-change): ответ на «что сейчас по YFS?» собирается из задач, знаний, watchers, напоминаний — не просто список поисковых хитов. Это производный взгляд, не вторая база.

## 6. Projects

Project — рабочий контейнер Owner’а. Не тема чата и не группа Telegram.

Проект может быть связан с разговорами, людьми, задачами, файлами, Knowledge, событиями, Telegram-группами. Сам проект (имя, статус, описание) остаётся источником истины. Knowledge только индексирует.

Обычному пользователю проекты **недоступны**.

Вопрос «что по YFS?» для Owner’а идёт в синтез текущего состояния. Инструмент «сырого» контекста проекта (`get_project_context`) остаётся отдельно. Магического «здоровья 73%» нет: есть факты вроде «заблокирован», «ждём внешнее», «риск дедлайна», «нет недавней активности».

## 7. Tasks

Task = работа, которую нужно сделать.

Примеры: «Сделать ответ Apple», «Проверить новый билд», «Подготовить презентацию».

У задачи бывают статус (`open` / `in_progress` / `completed` / `cancelled`), приоритет, дедлайн, одна ступень подзадач, связь с проектом (Owner), связь с напоминанием, ссылка на исходный чат.

Задача — не напоминание. Закрытие задачи отменяет будущие связанные напоминания, история доставки остаётся.

Центр **Задачи**: Просрочено / Сегодня / Предстоящие / Без срока / Выполненные.

Статус core Task Center (создание, подзадача, закрытие, связь с напоминанием) в Core Daily Workflow: **MANUAL PASS**. Briefs, proactive и Notification Center как полный продукт — **IMPLEMENTED / NOT VALIDATED**.

## 8. Reminders

Reminder = известное время.

**Вы:** «Напомни завтра в 10 позвонить Marco.»

| | Task | Reminder |
| --- | --- | --- |
| Смысл | Что сделать | Когда напомнить |
| Пример | «Сделать отчёт» | «Напомни завтра в 9» |

Напоминание — объект ядра. Telegram и Web Push — только доставка. Можно получить Push, Telegram, оба или ни одного: само напоминание всё равно существует.

Живой базовый поток (создать, центр, Web Push) Owner подтвердил: **MANUAL PASS for confirmed live core flow**. Исчерпывающие края (все DST, все устройства, все сбои доставки) — **не** MANUAL PASS.

## 9. Watchers / автоматизации

Watcher = условие **будущего** события, которое вы явно задали.

**Вы:** «Если Apple ответит, сообщи мне.»  
**Вы:** «Когда в репозиторий придёт новый commit, скажи.»  
**Вы:** «Если в пятницу задача всё ещё открыта, напомни.»

| | Reminder | Watcher |
| --- | --- | --- |
| Когда | В пятницу в 18:00 | Когда условие станет истинным |
| Пример | «напомни в пятницу» | «напомни в пятницу, **только если** задача ещё открыта» |

Что делает watcher:

1. ждёт условие
2. проверяет свой источник (задача, Knowledge, почта Owner’а…)
3. при срабатывании создаёт **occurrence** (факт срабатывания)
4. уведомляет
5. может создать Task или Reminder
6. может **предложить** внешнее действие

Первая проверка ставит «нулевую точку»: старая почта и старые коммиты сами по себе не стреляют.

Watcher **не** отправляет Gmail, не пишет в Calendar и не пушит в GitHub молча. «Если клиент ответит да, отправь договор» → уведомление «клиент ответил, отправить договор?» а не автоматическая отправка.

Обычный пользователь: внутренние источники (задачи, напоминания, Knowledge). Gmail/Calendar/GitHub-watchers — Owner.

Статус: **MANUAL PASS** для внутреннего task watcher flow в Core Daily Workflow. Внешние интеграции (Gmail / Calendar / GitHub) и цепочка proposed action → confirmation → external write остаются **IMPLEMENTED / NOT VALIDATED**. Jarvis может **предложить** поставить watcher («ты часто ждёшь ответы Apple»), но не создаёт его сам.

## 9.1 Scheduled Reports / отчёты

Отчёт — не напоминание и не watcher. В известное время Jarvis **собирает источники** и присылает одну сводку.

Примеры: каждый вечер в 22 планы на завтра; каждое утро в 8:30 планы на сегодня; каждое утро в 9 новые письма и группы.

Центр **Отчеты**. Настройка через чат. Статус: **IMPLEMENTED / READY FOR OWNER VALIDATION**.

## 10. Proactive assistant

Два разных механизма.

**Watcher** — вы сами сказали условие, оно сохранено.

**Proactive** — система сама замечает узкий набор ситуаций (просроченная задача, дедлайн близко, слишком долгое ожидание, риск по проекту) и может положить подсказку в уведомления.

Защита от спама (фактические правила):

- по умолчанию **выключено**, в том числе у Owner
- не больше **3** проактивных подсказок в локальные сутки
- пауза **4 часа** по одному источнику-задаче
- тихие часы и уникальный ключ, чтобы одно событие не дублировалось

Это не «скрытый агент, который всё делает сам». Внешние письма он не шлёт. Статус: **IMPLEMENTED / NOT VALIDATED**.

Daily / Weekly briefs — отдельная opt-in рассылка (тоже по умолчанию выключена). Планировщик тот же, второго «ежедневного Jarvis» нет.

## 11. Notifications

**Notification Center** — входящие внутри Workspace. Это не то же самое, что Web Push, и не то же самое, что список напоминаний.

Типы, среди прочих: срок напоминания, срок / просрочка задачи, готов brief, проактивная подсказка, сработал watcher.

Уведомление существует **независимо** от канала доставки:

- видно в панели Уведомления
- Web Push может сопровождать (базовый reminder flow — MANUAL PASS)
- Telegram **по умолчанию не** используется для событий Notification Center; у напоминаний своя опциональная Telegram-доставка

Сбой Push не удаляет строку из inbox.

Статус центра задач/briefs/proactive: **IMPLEMENTED / NOT VALIDATED**.

## 12. Telegram

Telegram — дополнительный канал. **Не** второй Jarvis.

```
Telegram DM (текст)
  → тот же Core
  → ответ текстом или голосом (как настроено)

Telegram voice note
  → Gemini STT
  → тот же Core
  → текст или голосовой ответ (ElevenLabs)
```

После pairing появляется чат **Основной**. Меню бота («Чаты», «Новый чат») в смысловую историю не пишется.

Голосовой **ответ** в Telegram (`sendVoice`): **MANUAL PASS**.  
Голосовой **вход** (voice note → распознавание): **IMPLEMENTED / NOT VALIDATED**.  
По умолчанию бот отвечает **текстом**. Можно выбрать `text` / `voice` / `auto`.

**Группы** (Owner): бот может хранить сообщения группы и строить group knowledge. Это **не** личная память. В личный чат группа сама не отвечает, пока политика группы этого не требует. Живая кампания групп: **IMPLEMENTED / NOT VALIDATED**.

Диалог Beta (realtime ElevenLabs) **на Telegram не включается**.

## 13. Voice

Голос — режим того же разговора, не отдельная личность.

### Рация (по умолчанию, стабильный путь)

Нажать и держать → запись → отпустить → Gemini распознаёт речь → Jarvis думает → ElevenLabs озвучивает ответ.

Owner подтвердил конвейер: микрофон, запись, STT, ответ, TTS, выбор голоса. **MANUAL PASS** для этого пайплайна.

### Диалог Beta

Постоянное слушание через ElevenLabs realtime: определение конца фразы, можно перебить, живой STT/TTS. Мозг по-прежнему Jarvis Core.

**IMPLEMENTED / NOT VALIDATED.** Выключен, пока не настроены флаги окружения. Рацию не удаляют, пока Owner не проведёт живое сравнение.

Один и тот же выбранный голос (шесть готовых: Jessica, Sarah, Lily, Eric, George, Chris) используется в Web и в Telegram TTS.

## 14. Интеграции

Интеграции — **инструменты** Jarvis. Они не становятся отдельными агентами.

| Интеграция | Кто | Статус |
| --- | --- | --- |
| Google Calendar | Owner | Код есть, **живая кампания не валидирована** |
| Gmail | Owner | Код есть, **живая кампания не валидирована** |
| GitHub | Owner | Код есть, **живая кампания не валидирована** |
| Веб-поиск (Gemini Google Search) | Owner MANUAL PASS выбранных сценариев; capability также у обычного пользователя | Tavily / `fetch_web_page` как отдельная проверка — нет |
| Telegram | Owner настраивает бота; пользователь связывает свой аккаунт | pairing в продукте |
| Storage | файлы пользователя; страница библиотеки Owner | загрузка текстового файла через чат — MANUAL PASS |
| ElevenLabs | TTS для голоса | пайплайн Рации — MANUAL PASS; не «агент ElevenLabs» |

Нет Google Drive. Нет зеркала всего почтового ящика. Calendar и Gmail — живые API в момент вопроса, не локальная копия всей почты. GitHub — инструменты к API, не локальный git и не merge/force-push.

Синтез **сам** почту и GitHub не опрашивает. Если спросить «что **сейчас** в GitHub?» при устаревших наблюдениях, Jarvis должен взять живой GitHub-инструмент, а не притворяться, что индекс свежий.

## 15. Политика подтверждений

Чтение доступных вам данных — без отдельного «да», если есть право.

Внутренние действия по прямой команде обычно выполняются сразу:

- создать / изменить задачу
- создать / отложить / закрыть напоминание
- создать / поставить на паузу watcher
- обновить профиль ассистента

Внешние и опасные действия требуют подтверждения по правилам:

| Действие | Поведение |
| --- | --- |
| Прочитать календарь / письмо / репозиторий | можно, если доступ есть |
| Отправить Gmail | **всегда** подтверждение, даже если вы написали «отправь» |
| Удалить событие календаря | **всегда** подтверждение |
| Модель сама предложила внешнюю запись | подтверждение |
| Явная команда на GitHub-write (issue, comment, PR create) | можно; merge/delete/force нет |
| Watcher предлагает «отправить договор» | только предложение, не отправка |

Пример:

**Вы:** «Если клиент ответит да, отправь договор.»

Jarvis не отправляет договор автоматически. Он ждёт ответ (watcher) и потом спрашивает: «Клиент ответил да. Отправить договор?»

Подтвердить можно кнопкой или короткой фразой вроде «да» / «подтверждаю». «Нет» / «отмена» — отмена. Истекающая заявка повторно не исполняется. Модель не может подтвердить сама себя.

---

## 16. Файлы

Два разных вида.

**Постоянное хранилище (Storage)**  
Файл живёт независимо от чата. Можно прикрепить в сообщении и потом снова найти. Сырые байты не кладутся в Memory.

**Временное вложение**  
Скриншот / картинка сообщения. Байты позже чистятся; может остаться короткий визуальный summary. Это не библиотека документов.

Jarvis может разобрать изображение текущего хода (Owner: vision — MANUAL PASS) и текст файла (загрузка текстового файла — MANUAL PASS). Исторические картинки в модель пикселями не переигрываются.

Страница `/jarvis/storage` — только Owner. Обычный пользователь прикрепляет файлы в `/chat`; отдельной страницы библиотеки у него нет. Деструктивное удаление файла и чистка скриншотов как отдельные живые проверки — **не** MANUAL PASS.

---

## 17. Контекст (зачем не вся история)

Jarvis **не** отправляет модели всю историю целиком. Иначе с ростом переписки росли бы цена, задержка и шум.

На один вопрос собирается ограниченный пакет:

- текущая реплика (её не выкидывают)
- последние сообщения этого чата
- working context (о чём сейчас речь, недавние сущности, недавние задачи)
- компактная Memory
- крошечный Knowledge / синтез, если уместно
- summary более старого куска
- результаты инструментов этого хода

Старое обычно приходит через **summaries**. Полный старый текст — только если модель явно ищет (`search_conversation_history`).

Это держит скорость, стоимость и качество, когда истории уже много. Голосовые расшифровки — обычные сообщения, отдельного «безлимитного голосового окна» нет.

## 18. Изоляция пользователей

У каждого пользователя свои:

- разговоры
- Memory
- Knowledge
- задачи и напоминания
- watchers
- уведомления
- файлы

Пользователь A не видит данные B. Owner не читает чужой `/chat` по прямой ссылке. Impersonation в Admin — отдельный явный режим с баннером, не «тихий bypass» Personal Workspace.

Нет публичной регистрации.

## 19. Персонализация

Можно настроить:

- имя ассистента, характер, стиль общения
- краткое «обо мне» из знакомства
- дополнительный General Prompt (постоянные инструкции)
- голос озвучки
- режим ответа Telegram (текст / голос / авто)
- продуктивность: briefs и proactive (по умолчанию выкл)

Команда «отвечай сейчас коротко» — **временный** стиль текущего чата. Она не обязана переписывать постоянный профиль.

Знакомство («Познакомиться») — обычный чат, не форма-мастер. Owner подтвердил, что вход в знакомство **появляется** (MANUAL PARTIAL). Полное прохождение и смена профиля E2E — **не** MANUAL PASS. Чат без онбординга не блокируется.

У Owner шапка остаётся **Jarvis**. У обычного пользователя — выбранное имя ассистента, иначе «Assistant».

## 20. Примеры реального использования

**A. Напоминание**

> Напомни завтра в 10 отправить отчёт.

→ Reminder на завтра 10:00 в вашем часовом поясе.

**B. Задача**

> Создай задачу проверить новый билд.

→ Task в центре Задачи.

**C. Watcher**

> Если Apple ответит, сообщи.

→ Watcher на входящее (Owner, Gmail). История ящика не «догоняется».

**D. Состояние проекта**

> Что сейчас по YFS?

→ Синтез: открытые задачи, недавние события, ожидания, блокеры. **MANUAL PASS** для проверенного core synthesis в Core Daily Workflow; не все edge cases. Для Owner.

**E. Люди**

> Кто занимается дизайном YFS?

→ Knowledge: человек ↔ проект. Если связи нет — так и скажет, не выдумает CRM.

**F. Старый разговор**

> Что мы обсуждали неделю назад по Meta?

→ summaries текущего/других чатов, при необходимости поиск истории. Не «вся жизнь в одном промпте».

**G. Запомнить**

> Запомни, что Marco предпочитает общаться по email.

→ устойчивый факт (Memory) и/или сущность человека (Knowledge), в зависимости от смысла. Не каждая фраза становится и тем и другим.

**H. Календарь**

> Посмотри моё расписание завтра.

→ живой Google Calendar (Owner). Код есть, живая кампания **не** валидирована.

**I. Письмо**

> Напиши письмо клиенту, что согласны по срокам.

→ черновик / отправка Gmail. Отправка **только после подтверждения**.

**J. Голос**

Зажать Рацию, сказать то же самое — тот же Core, тот же чат, ответ голосом.

## 21. Сквозной сценарий: проект YFS

Утро. Если включён Daily Brief (по умолчанию выкл), в уведомлениях появляется сжатый обзор: слоты дня, дедлайны, ожидания, топ внимания. Briefs: **IMPLEMENTED / NOT VALIDATED**.

Owner открывает `/jarvis` и пишет:

> Что по YFS?

Jarvis (через синтез, не через «угадайку») может увидеть, например:

- открытая задача «ответ по контракту»
- вчерашний GitHub-event, уже попавший в Knowledge
- ожидание ответа клиента (watcher или явное waiting-for)
- встреча завтра
- freshness: «GitHub наблюдался N часов назад» — индекс, не live API

> Если клиент ответит по контракту, скажи мне.

Создаётся watcher. Старые письма не стреляют.

Позже условие выполняется. Появляется уведомление (центр + при возможности Push). Jarvis **не** отвечает клиенту сам.

> Что он написал?

Jarvis читает письмо инструментом Gmail (Owner). Полное тело не складывается в Knowledge как сырой дамп.

> Ответь, что согласны.

Jarvis готовит отправку и **спрашивает подтверждение**. Только после «да» письмо уходит.

На таймлайне Knowledge может появиться событие. Задачу вы закрываете явно. Watcher one-shot завершается. Синтез в следующий раз уже не показывает то же ожидание.

Ни один шаг этого сценария не требует, чтобы Jarvis стал автономным агентом.

## 22. Что JARVIS сейчас не делает

Не считать продуктом:

- Desktop-клиент, трей, глобальный хоткей — **CANCELLED**
- Mobile как основной интерфейс и отдельный Client API — **DEFERRED**
- неограниченный автономный агент, который сам пишет во внешний мир
- автоматические внешние записи без подтверждения
- Google Drive
- полная CRM-копия контактов
- графовая БД Neo4j
- массовый автоскан всей почты/жизни «на всякий случай»
- скрытый background-агент, который «всё делает сам»
- публичная регистрация
- wake word
- realtime-стрим планировщика в браузер (события приходят при открытии, Push или навигации)

Phase E (Knowledge + Watchers + Synthesis) в коде есть. Проверенный core flow каждого слоя — **MANUAL PASS** в Core Daily Workflow. Слой **как целое** (все edge cases, внешние watchers, live Gmail/Calendar/GitHub) **не** закрыт.

## 24. Архитектура простыми словами

```
   Web Workspace     Telegram DM      Голос (Рация / Beta)
         \               |                    /
          \              |                   /
           ▼             ▼                  ▼
                    JARVIS CORE
                         │
              Conversation Engine
                 /       |        \
            Memory    Knowledge    Tools
                         │
            Tasks / Reminders / Watchers
                         │
         Integrations          Notification Center
         (Gmail, Calendar,           │
          GitHub, Search)      Web Push / Telegram*
```

\* Telegram — опциональная доставка напоминаний, не основной inbox центра.

Отдельно: **база данных — источник истины**. Чаты, факты, задачи, watchers, профили живут там. Модель каждый ход получает только ограниченный пакет. ElevenLabs в Диалоге Beta помнит транспортный разговор — это не каноническая память Jarvis.

Канал (Web, Telegram) не думает сам. Он нормализует вход и показывает выход.
